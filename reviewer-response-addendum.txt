ITEM 1c - CUSTODY MODEL, STATED ACCURATELY
--------------------------------------------
You are correct, and we adopt the correction: platform-managed keys are not
self-custody. Our earlier "non-custodial pivot" framing was accurate for Path A and
inaccurate as a description of the product, because Path B exists and is custodial.

  Path A - wallet connect: SELF-CUSTODY. Key lives in the user's browser extension.
           The user signs; we never see the secret. SEP-10 proves account ownership
           and establishes an httpOnly cookie session.

  Path B - Google email/OAuth: CUSTODIAL, platform-held. backend/src/services/account.ts
           calls Keypair.random() server-side, Friendbot-funds the account, and keeps
           the secret in a process-local Map. The user cannot export it, cannot
           independently sign with it, and cannot recover it. PathPulse can sign
           without the user's participation. That is custody, and we hold it.

Two further properties of Path B that we would rather you hear from us:

  - The keys are in-memory only. Nothing is persisted, so every managed account is
    orphaned on process restart or redeploy - the funds become permanently
    unspendable. This is prototype-grade and is not a custody model we would put in
    front of a real user.
  - Even the substitution is a custody downgrade relative to what was committed.
    Privy's embedded wallets are non-custodial by construction; what we shipped in
    their place is not. We are not presenting Path B as equivalent to the commitment.


One more correction to this section, found while preparing the evidence for item 1d
and fixed before this document reached you. The delegated-signing endpoint
POST /v1/tx/build took its userId from the request body and never consulted the
session. Any unauthenticated caller who knew a user id - a value we hand to the
client in the Google verify response - could have the backend delegate-sign an
arbitrary payment out of that user's managed wallet. So the accurate statement of
Path B custody as it stood was not merely "the platform holds your key" but "the
platform will sign with your key for anyone who presents your user id."

That endpoint now requires a session and derives the signing identity from it,
ignoring any userId in the body. The defect was reachable in practice only from
today: until the store-wiring fix above, no end-user account existed in the signer's
store at all, so there was nothing for it to sign from. We are reporting it because
it bears on the custody question you asked, not because it produced any transaction -
no delegated transaction has ever been submitted from an end-user managed account
other than the two we cite in this document.

ITEM 1d - THE REQUESTED MANAGED-ACCOUNT TRANSACTION: DEFECT FOUND AND FIXED
-----------------------------------------------------------------------------
You asked for one managed account provisioned via the email/OAuth flow, with a
transaction it signed through the delegated path. That was not producible when your
review was written, for a reason worth stating precisely: it was a defect, not a
missing artifact.

The email/OAuth flow and the delegated-signing path used two different, disconnected
in-memory stores:

  POST /v1/auth/google/verify
      -> ensureAccountForEmail()          backend/src/services/account.ts
      -> wrote to  accountsByEmail        (its own keypair; no Signer was ever built)

  POST /v1/tx/build
      -> getManagedWallet(userId)         backend/src/stellar/transactions.ts:55
      -> read from  store                 backend/src/stellar/managed.ts:25

Nothing wrote an end user into the second store - provisionManagedWallet() was called
only by our four internal service accounts. So a user who signed in with Google
received a funded managed address, and every delegated transaction from it returned
404. The error text directed the caller to POST /v1/onboard, a route removed during
the auth pivot and never cleaned up.

Fixed. ensureAccountForEmail now provisions through provisionManagedWallet(), so the
sign-in flow and the signer read one keypair. Verified end to end against testnet
before deployment - email account provisioned, transaction built and delegate-signed
by the backend, submitted and accepted:

  hash 3f821aada476112145778ecefa1c7347052632d5fdcac28d50fede35ba9af054
  ledger 4327411, successful

That hash is offered only as proof the path works. It came from a local run with a
synthetic address, not from the deployed sign-in, so it is not the measure.

One property of that flow you should weigh, because the fix does not change it: the

satisfiable and reproducible on demand, but the specific account behind any given
hash does not survive the next deployment.

THE ORIGINAL TREASURY IS FROZEN - AND A REPLACEMENT IS NOW LIVE
-----------------------------------------------------------------
We must disclose that the account above can never authorize anything, and then show
you what we did about it.

The three non-master signer secrets are not in our possession. The provisioning
script printed them to stdout once and never wrote them to disk; the checked-in
account file holds public keys only; no secret is in any .env, commit, or shell
history on the machine that has them. The master key alone carries weight 1 against a
threshold of 2, so it cannot authorize a payment - and equally cannot authorize a
set_options to repair its own signer set. The account is frozen in the configuration
